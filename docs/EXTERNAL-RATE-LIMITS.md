# 외부 Git·AI 호출 제한과 재개

V15부터 GitHub/GitLab 및 Ollama/LiteLLM/OpenAI가 HTTP429를 반환하면 현재 리뷰 요청을 DB 대기 상태로 돌린다. 작업자와 프로젝트 잠금을 해제하며, 같은 요청의 접수자·최초 접수 시각·이미 저장한 커밋 리뷰와 이슈를 유지한다. 프로젝트 상세·리뷰 기록에는 제한된 서비스와 UTC 초 단위 재시도 가능 시각이 표시된다. 이 시각은 실행 가능한 가장 이른 시각이며 시작 시각 보장은 아니다.

## 대기 정책

- `Retry-After`의 정수 초와 HTTP 날짜 3형식을 처리한다. 최소30초, 헤더 누락·중복·잘못된 값은60초를 적용한다.
- 유효한 대기값이24시간을 넘거나 숫자 범위를 넘으면 자동 재시도를 중단한다.128자 초과 헤더도 해석하지 않고 중단한다. 긴 숫자를 짧은 기본 대기로 바꾸지 않는다.
- 실제429 응답 횟수에 따른 요청 대기는60·120·240·480·960초이며, 공급자 힌트나 공유 대기가 더 길면 그 시각을 따른다. HTTP 전 공유 대기를 발견한 경우 실제429 횟수를 늘리지 않는다. 요청의 대기 계산에는 최대1시간 backoff 상한이 있다.
- 최대5회 대기 후 여섯 번째 실제429에서 중단한다. 첫 제한 대기부터24시간이 지나거나 다음 대기가 그 범위를 넘으면 중단한다. 재시작으로 횟수나24시간 기준을 초기화하지 않는다.
- 중단된 요청은 `RATE_LIMIT_EXHAUSTED`로 표시하고 이후 정시 예약으로 다시 접수하지 않는다. 서비스 상태를 확인한 사용자 또는 관리자가 직접 새 요청을 접수하면 새 예산으로 시작하며 저장된 리뷰는 재사용한다.
- 대기 중 다시 누르는 수동 요청과 정시 예약은 기존 요청에 합쳐진다. 재시도 시각을 앞당기거나 횟수를 초기화하지 않는다. 프로젝트 중지·계정/접근 권한 변경은 재개 전에 다시 검사한다.

429 본문은 읽지 않고 취소한다.403·5xx·시간 초과·잘못된 AI 출력은 이 자동 대기 정책에 포함하지 않으며 기존 실패 처리한다. GitHub의403 기반 quota 응답 등 공급자 고유 상태까지 자동 분류하지 않는다.

헤더 형식은 [RFC9110 Retry-After](https://www.rfc-editor.org/rfc/rfc9110.html#name-retry-after),429 의미는 [RFC6585](https://www.rfc-editor.org/rfc/rfc6585.html#section-4)를 따른다. 횟수·시간·길이 상한과 기본 대기는 이 제품의 정책이다.

## 여러 서버의 공유 범위

`integration_cooldown`은 Git/AI 구분과 정규화한 origin(스킴·소문자 호스트·실효 포트)의 SHA256으로 대기를 공유한다. URL 경로·query·자격증명·모델별로 구분하지 않으므로 같은 서비스 주소를 쓰는 다른 프로젝트에도 보수적으로 적용된다. Git와 AI는 같은 origin이어도 별개다. 전체 URL·응답 본문·원문 헤더·토큰은 이 테이블과 대기 감사 이벤트에 저장하지 않는다. 해시는 원문 추측을 막는 익명화 보장이 아니다.

HTTP 요청 직전에 공유 대기를 확인하고,429 수신 후 별도 트랜잭션에서 기록한다. 서비스별 고정 guard 행 잠금으로 동시 기록의 더 긴 시각을 보존한다. 저장소 오류는 외부 호출을 허용하는 결과로 바꾸지 않으며 미완료 요청을 기존 DB 복구 경로로 남긴다. SQL/트랜잭션 시간 제한은3초이고 연결 풀·소켓 대기는 별도다.

서비스별 최대10,000개 origin을 보존하며 용량 초과는 기존 행을 지우지 않고 실패한다. 만료 행은 읽을 때 대기를 만들지 않고, 같은 서비스의 다음429 기록 때 정리한다. 추가429가 없으면 만료 행이 물리적으로 남을 수 있다. 사용자·프로젝트별 이력 보존 정책과 별도로 관리한다.

이미 외부 호출을 시작한 다른 작업은 취소되지 않는다. 공유 확인과 HTTP 전송은 하나의 원자 연산이 아니므로 순간적인 동시 호출을 완전히 직렬화하지 않는다. 저장 전에 실패한 커밋의 AI 분할 결과는 재호출될 수 있다. 저장 완료한 SHA만 재사용하므로 외부 호출·과금의 정확히 한 번 실행을 보장하지 않는다.

앱 서버와 DB의 시계를 NTP 등으로 동기화해야 한다. 공급자 응답은 앱에서 절대 UTC 시각으로 해석하고 DB 시계로 공유 만료를 확인하므로 큰 시계 오차는 다른 서버의 대기 길이와 요청24시간 예산에 영향을 준다. 시간 오차를 자동 보정하는 기능은 아니다.

## 업데이트·복원

V15는 기존 `review_request`에 실제429 횟수와 첫 대기 시각을 추가한다. 기존 요청은0회·미기록 상태를 유지한다. 새 공유 guard에는 Git/AI 두 행만 생성하고 대기 테이블은 비어 있다. 기존 리뷰·이슈·진행 기준을 초기화하지 않는다.

업데이트 시 모든 기존 앱을 중지하고 백업한 뒤 같은 버전으로 전환한다. V14 앱은 새 공유 제한을 따르지 않으므로 혼합 운영하지 않는다. 롤백은 업데이트 전 백업을 새 DB에 복원하고 구 WAR로 전환한다. 새 V15 데이터를 역변환하지 않는다. 현재 백업 검증 대상은14개 테이블이며 공유 대기와 요청 재시도 상태도 포함한다.

오래된 백업에는 복원 시점 이후의 공급자 제한 정보가 없다. 복원 후 `REVIEW_ENABLED=false`와 `REVIEW_WORKER_ENABLED=false`를 유지하고 공급자 상태를 확인한 뒤 재개한다. DB 직접 수정으로 실제 대기를 우회하는 절차는 제공하지 않는다.

## 검증 범위

단위·통합 검증은 헤더 경계, 본문 취소, 공급자5종, 같은 요청 보존, 저장 SHA 재사용, 횟수/시간 상한, 권한 변경, fencing, SQL 롤백과 UTC 안내를 다룬다. 실제 PostgreSQL 검증은 독립 연결의 동시 기록·잠금 시간 초과·DB 시계·용량·V14 데이터 보존을 다룬다. 최신 실제 실행 결과는 `WORK.md`에 기록한다.

Linux 부모 도구의 `--review-rate-limit`는 로컬 합성 Git/AI와 실제 WAR를 사용한다. 일부 대기 시각을 소유한 시험 schema에서만 SQL로 만료시켜 경계를 검증하므로 실제 공급자 quota 회복이나24시간 연속 운영을 검증한 것으로 해석하지 않는다. 운영 LiteLLM 주소·모델 및 실제 호출 제한·비용 검증은 별도다.

Linux native checkout에서 아래처럼 실행한다. 부모는 별도 `.local/pg-validation`을 시작하여 전체 Java·필수PG 검증 후 하위 도구를 호출하고 종료한다. 기존 서비스나 다른 클러스터를 시험용으로 전환하지 않는다.

```bash
python3 scripts/test-postgres-linux.py \
  --pg-bin /usr/lib/postgresql/17/bin \
  --java /usr/lib/jvm/temurin-25-jdk-amd64/bin/java \
  --review-rate-limit
```

시험 WAR 포트 기본값은18096이며 `--review-rate-limit-port`로 변경할 수 있다. 하위 도구는 실제 AI429→동일 origin 다른 프로젝트 AI 무호출→재시작 뒤6초 무호출→소유 시각 만료→Git429→다시 만료 후 미완료 커밋만 저장을 검증한다. A 커밋은 AI1회·B는 최초429와 성공을 합쳐2회이며 결과는2커밋/2이슈다. 실제 JSP의 대기·UTC 표시와 직접 재요청 안내를 확인한다. 한도 중단 화면은 마지막 요청의 SQL 합성 상태·예약 OFF 조건이며 실제24시간/6번째429 시험은 Java 회귀와 구분한다.

보고서는 이번 호출의 `.local/linux-postgres-<실행 토큰>/review-rate-limit-<실행 토큰>.json`에 생성한다. PASS는 소유 WAR·schema·임시 작업 경로 정리와 원본14개 테이블 보존까지 필요하다. 대기 헤더·HTTP 본문·계정 비밀번호·원본 DB 행과 지문 값은 보고하지 않는다. 실패·취소 시 사유 분류와 확인된 정리 결과를 남긴다.

### 두 서버의 실제 시간 대기

`--review-rate-limit-wallclock`는 SQL로 요청·공유 대기 시각을 바꾸지 않는다. 두 WAR와 같은 UUID 시험 schema, 서로 다른 loopback Git origin X/Y, 합성 AI만 사용한다.

```bash
python3 scripts/test-postgres-linux.py \
  --pg-bin /usr/lib/postgresql/17/bin \
  --java /usr/lib/jvm/temurin-25-jdk-amd64/bin/java \
  --review-rate-limit-wallclock
```

WAR 포트는18097/18098이며 `--review-rate-limit-wallclock-port-a`와 `--review-rate-limit-wallclock-port-b`로 변경한다. 함께 선택한 다른 검증 포트와 중복되면 시작 전에 거부한다. 전체 Java·필수PG 검증을 먼저 통과해야 하위 검증을 실행한다.

1. 서버 A가 origin X의 `Retry-After: 65`를 받고 같은 요청을 대기 상태로 보존한다.
2. A를 중지한 상태에서 서버 B가 같은 X의 다른 프로젝트를 처리한다. DB 공유 대기로 전환되고 실제429 횟수는0이며 X HTTP 호출은 늘지 않아야 한다.
3. B의 단일 작업자가 별도 origin Y의 프로젝트를65초 안에 완료해야 한다. A도65초 안에 다시 시작하여 이후 두 WAR가 살아 있는 상태를 확인한다.
4. X의 첫429 응답 헤더 전 monotonic 시각을 하한으로 삼아 이후 모든 X Git 요청이65초 이후인지 검사한다. 전체 도착 기록을 확인하므로 중간 polling 간격의 조기 호출도 실패한다. 실제 후속 호출이 없으면 통과하지 않는다.
5. X의 두 요청이 원 ID·요청자·접수 시각을 유지하며 각각2커밋/2이슈로 완료되어야 한다. 중복 AI 호출·저장이나 누락이 있으면 실패한다.

하위 도구의 기본 전체 제한은240초(설정120~600초)다. 느린 기동으로65초 관찰 구간을 놓쳐도 성공으로 처리하지 않는다. 보고서는 `.local/linux-postgres-<실행 토큰>/review-rate-limit-wallclock-<실행 토큰>.json`이며 소유 WAR/schema/work 정리와 기존14테이블 보존이 모두 확인되어야 PASS다. 취소는 FAIL/종료130을 유지한다.

이 시험은 로컬65초·프로젝트3개 범위의 증거다. 실제 공급자 quota·TLS/proxy·서버 간 시계 오차·24시간/6번째429·장기 공정성·임의 부하의 시작 SLA를 검증하지 않는다. 두 서버가 모두 살아 있음을 확인하지만 재개 작업을 각 서버가 반드시 하나씩 담당하는 것은 아니다.
