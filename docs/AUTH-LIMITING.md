# 로그인·가입 시도 제한 공유

V14부터 같은 PostgreSQL DB를 사용하는 모든 앱 서버가 로그인·가입 시도 횟수를 공유한다. 서버 재시작이나 다른 서버로의 요청 전환으로 새 할당량을 얻지 않는다. 사용자에게는 횟수 초과 시429와 남은 대기 시간, 제한 저장소를 확인할 수 없을 때는503과 잠시 후 재시도 안내를 표시한다.

## 유지하는 정책

| 구분 | 기본 횟수·창 | 성공 처리 | 용량 |
|---|---|---|---|
| 로그인 | 계정10회, IP100회 / 첫 허용 시도부터900초 | 계정만 초기화, IP 유지 | 계정/IP를 합쳐10000개 버킷 |
| 가입 | IP10회 / 첫 허용 시도부터900초 | 횟수 유지 | 기존과 같이 주소당2개 내부 버킷, 총10000개 |

거부된 재시도는 횟수나 만료를 연장하지 않는다. 새 키 때문에 공간이 부족하면 기존 계정을 축출하지 않고 거부한다. 이미 존재하는 키 쌍은 자기 횟수가 남아 있으면 계속 사용할 수 있다. 로그인과 가입의 공간·횟수는 서로 독립적이다.

계정 키는 기존과 같이 ASCII trim·Unicode strip·소문자 변환 뒤SHA256을 사용한다. IP는 Servlet의 `getRemoteAddr()`를 사용한다. 비밀번호와 원문 계정/IP는 이 테이블에 저장하지 않는다. 해시된 IP·계정도 추측 가능한 식별자이므로 익명 정보로 취급하지 않는다. 프록시가 제공한 주소를 사용할 때는 [신뢰 프록시 설정](LINUX-DEPLOYMENT.md)을 먼저 검증한다.

## 저장·동시 처리·실패

- `auth_attempt_policy`의 LOGIN/SIGNUP 두 행을 각각 잠그고, PostgreSQL 시계를 읽어 만료를 처리한다. 계정과 IP의 확인·증가를 한 트랜잭션으로 commit한다. 두 번째 저장이 실패하면 첫 증가와 그 트랜잭션의 만료 삭제도 되돌아간다.
- HTTP 요청 바깥의 별도 트랜잭션으로 저장하므로 로그인 실패나 호출자의 rollback이 이미 소비한 횟수를 되돌리지 않는다. SHA 키만 SQL에 전달한다.
- 전용 SQL·트랜잭션 제한은3초다. DB pool 연결 대기·네트워크/socket 제한은 [JDBC 설정](OPERATIONS.md)의 별도 한도가 적용되므로 전체 HTTP 응답이 반드시3초 안에 끝난다는 보장은 아니다.
- DB 오류·잠금 초과·정책 불일치 시 처리를 진행하지 않고503, `Retry-After: 30`, `Cache-Control: no-store`와 고정 안내를 반환한다. SQL·드라이버 예외·입력값을 응답에 붙이지 않는다. 일반 횟수/용량 초과는429다.
- 인증 성공 뒤 계정 버킷 삭제만 실패하면 이미 소비한 제한을 유지하고 성공 응답을 마친다. 계정 삭제 실패를 이유로 인증된 세션과 실패 화면이 함께 남게 하지 않는다. IP 제한은 삭제하지 않는다.
- 요청 때 만료 행을 삭제하며, 별도 주기 작업도1분마다 scope별 짧은 트랜잭션으로 삭제한다. 모든 서버가 멈췄거나 DB가 실패하면 실제 삭제는 재개 후로 늦어지지만 만료한 행은 새 요청의 횟수로 세지 않는다. quota 정리까지 포함한 네 작업이 예약 풀4스레드를 사용한다. 높은 부하의 처리량이나 지연 SLA를 보장하는 설계는 아니다.

## 설정과 업데이트

Spring 설정은 기존 `app.security.login-account-attempts`, `login-address-attempts`, `login-window-seconds`, `login-max-entries` 및 `app.security.signup-address-attempts`, `signup-window-seconds`, `signup-max-entries`를 유지한다. 횟수는 양수, 창은1~86400초, 최대 버킷은2~1000000이다. 모든 서버에 같은 값을 적용한다.

첫 요청에서 scope의 설정 지문을 저장한다. 활성 버킷이 남아 있는데 다른 설정의 서버가 접근하면503으로 차단하며 한도를 조용히 바꾸거나 초기화하지 않는다. 해당 scope가 비면 새 설정을 채택할 수 있다. 설정 변경은 모든 서버를 함께 정지하고 이전 최대 창이 지나도록 기다린 뒤 동일 설정으로 재시작하는 방식으로 계획한다. 버킷을 수동 삭제하여 대기 시간을 우회하지 않는다.

V14 migration은 기존 사용자·프로젝트·리뷰·이슈를 보존하고 두 정책 행과 빈 버킷 테이블을 만든다. V13의 메모리 횟수는 이전할 수 없으므로 최초 V14 전환에서 새 창이 시작한다. 모든 구버전 서버를 먼저 정지하고 프록시 유지보수 제한을 유지한 상태로 교체한다. 실행 중인 V13 서버와 V14 서버의 혼합 운영으로 공유 제한이 적용된다고 보장하지 않는다.

## 백업·보존

전체 DB 백업에는 두 인증 제한 테이블도 포함된다. 복원은 백업 시점 횟수/만료와 정책 지문을 재현한다. 백업 이후 발생한 시도는 복원되지 않으므로 운영 복원 전후에는 프록시 제한·유지보수 상태를 유지한다. V12 백업으로 돌아가는 시험은 인증 제한을 유지하는 역방향 migration이 아니다.

만료 정리는 현재 DB에만 적용된다. 백업·WAL·로그의 별도 보존/암호화/삭제 정책은 운영자가 정한다. 제한 횟수·행 수를 늘리기 전에 예상 사용자 수와 DB/프록시 부하를 측정한다. 두 scope 안의 요청은 각각 직렬화되므로 무제한 인증 처리량을 가정하지 않는다.

## 검증

2026-10-03 WSL에서 빠른 H2/필터23건과 전체 Java924건 중914건이 통과했다(외부/선택 부하10skip). 필수PG5suite gate와 신규 PostgreSQL14건에서 서로 다른 연결의 계정/IP 동시 상한·용량 경쟁·rollback·잠금 제한·잠금 후 DB 시계·설정 충돌·V13 기존 자료 보존을 검증했다. 실제12테이블 백업/새 DB 복원과 V12→V14 WAR 업그레이드·V12백업복귀도 통과했다. 보고서는 Linux `.local/linux-postgres-9be02529b7c5458c9670100d1fc6655d`에 보존한다.

같은 날 `--shared-auth` 실행은 전체 Java924건 중914통과/10skip·필수PG gate 뒤, 실제 WAR 두 개의 다음 동작을60.882초에 확인했다. A는1회, B는강제 종료를 포함해2회 시작했다. Linux 보고서는 `.local/linux-postgres-56b7ff70bad6457ea422bdea2294b5a9/shared-auth-56b7ff70bad6457ea422bdea2294b5a9.json`이다.

- 두 서버를 번갈아 호출한 동일 계정10회 뒤 양쪽429, 거부 시 횟수·만료 불변, B 재시작 후에도 차단 유지
- 성공 로그인에서 계정 횟수만 제거하고 IP 유지, 가입10회 뒤 양쪽429·승인 대기 계정10명, 로그인/가입 scope 독립
- 다른 계정을 사용해도 두 서버 합산 IP100회 뒤 양쪽429
- 소유 버킷 테이블의 일시적 이름 변경으로 저장소 오류를 주입했을 때 양쪽 로그인/가입503·고정 안내·비밀/SQL 비노출·계정 미생성, 원복 뒤 기존 제한 유지
- SQL로 시험용 만료를 앞당긴 뒤 정상 요청 재개, WAR 둘 중지·소유 schema 제거·부모PG/lock 정리

HTTP 호출은 순차 교차 요청이며 실제 동시 증가 경쟁은 앞의 PostgreSQL 테스트에서 검증했다. SQL 만료·테이블 이름 변경은 명시적인 시험 주입이고 시간 경과나 실제 네트워크 단절을 대신하지 않는다. 이 시험은 loopback HTTP이며 운영 ingress/TLS·서버 장애 조합·장시간 처리량을 보증하지 않는다.

### 재현

전용 WSL 또는 Linux native checkout에서 일반 사용자로 실행한다. [WSL 환경·소유권 제한](WSL-VALIDATION.md)을 따르며 운영 DB를 지정하지 않는다. 부모 도구가 자신의 PostgreSQL17을 시작하고 clean 빌드·필수PG 검증 뒤 하위 도구를 호출한다.

```sh
python3 scripts/test-postgres-linux.py \
  --pg-bin /usr/lib/postgresql/17/bin \
  --java /usr/lib/jvm/temurin-25-jdk-amd64/bin/java \
  --shared-auth
```

기본 WAR 포트는127.0.0.1:18094·18095이며 `--shared-auth-port-a`·`--shared-auth-port-b`로 바꿀 수 있다. 선택한 모든 DB/WAR 포트는 서로 달라야 하고 기존 서버가 사용 중이면 중지시키지 않고 거부한다. 다른 검증 옵션과 함께 선택할 수 있다. `scripts/verify-shared-auth.py`는 부모가 준비한 `reviewer_integration`에 이번 호출의 UUID schema만 만들며 외부 Git·AI를 호출하지 않는다.

하위 도구는 schema OID·owner·표식을 확인하고 두 WAR의 종료가 확인된 뒤에만 schema를 제거한다. 소유권이 바뀌거나 종료를 확인할 수 없으면 실패로 보고하고 상태를 보존한다. 새0600 보고서는 기존 파일을 덮어쓰지 않으며 취소는 정리 후에도 FAIL/종료130을 유지한다. Windows/Linux의 도구 안전 경계17건과 부모 회귀43건을 포함한 전체 Python217건도 통과했다(Windows5skip, Linux10skip).

별도 일회성 Linux harness는 두 서버와 B 재시작 뒤 실제 가입이 시작된 시점에 하위 도구로 SIGTERM을 보냈다.28.676초, WAR 시작1/2회 상태에서 FAIL/KeyboardInterrupt/종료130을 유지하며 두 WAR·소유 schema·부모PG/lock을 정리하고 원본12테이블 지문을 보존했다. `.local/linux-postgres-3544d6040dd945e08038dfac5b70c0a1/cancel-harness.json`에 기록했다. 이 취소 실행은 Maven을 다시 실행한 것이 아니며 SIGKILL·전원 장애의 모든 시점을 검증하지 않는다.
