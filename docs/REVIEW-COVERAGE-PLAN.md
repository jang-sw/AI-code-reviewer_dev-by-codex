# 검토 범위 확장 설계안 — PROPOSED

작성: 2026-09-26. 기준: 현재 작업 트리의 `GitRepositoryClient`, `AiReviewClient`, `ReviewCoordinator`, `ReviewRepository`, 내부 이슈 화면 및 V1~V6 스키마.

**다음 회차 검토용 제안이다. 구현 완료 또는 승인된 요구사항이 아니다.** 특히 “검증된 미검토 파일을 수동 이슈로 넘기고 다음 커밋으로 진행”하는 정책은 현재 동작을 바꾸므로 별도 결정이 필요하다. 이 문서는 코드·설정·DB를 변경하지 않는다. 확정 요구사항은 [REQUIREMENTS.md](REQUIREMENTS.md), 현재 구현 계약은 [IMPLEMENTATION-CONTRACT.md](IMPLEMENTATION-CONTRACT.md)를 따른다.

## 1. 현재 확인한 제약

- GitHub는 커밋별 파일 목록·통계·본문 hunk를 검사한다. patch 누락, 본문이 없는 파일, 3,000개 파일 목록 한계 도달, 페이지·크기 예산 초과를 실패로 처리한다. patch 없는 rename/mode 변경을 동일 blob으로 입증하는 경로는 아직 없다.
- GitLab은 고정된 커밋과 첫 부모의 트리를 비교해 변경 경로를 확인한다. 동일 blob의 경로·모드 변경은 `METADATA_ONLY`, 파일 변경이 없는 검증된 커밋은 `EMPTY`다. binary, 누락·잘림, 변경 blob의 빈 patch는 실패한다. 정규 파일과 symlink 사이의 모드 변경도 수동 확인 대상으로 표시한다.
- `FULL`은 현재 지원하는 diff를 AI에 전달했다는 범위 분류다. 보안성 또는 결함 없음의 보증은 아니다. 본문과 메타데이터가 섞이면 본문과 경로·모드를 함께 전달한다.
- 현재 Git/AI diff 기본 상한은 각각 262,144 UTF-8 bytes다. AI는 JSON 입력·시스템 프롬프트·스키마·여유분을 포함한 보수적 byte 기준과 출력 예산을 context 한도와 비교한다. 따라서 diff 크기 상한 이하여도 context 한도로 실패할 수 있다. 임의 자르기는 하지 않는다.
- V5 범위는 `FULL/EMPTY/METADATA_ONLY`뿐이다. `METADATA_ONLY`는 명시적 안내만 남기며 자동 수동 이슈를 만들지 않는다. 이슈는 현재 AI 수정 권고이고 `severity`와 `file_path`가 필수다. 상태는 `OPEN/RESOLVED/DISMISSED`다.
- 커밋 결과·이슈는 한 트랜잭션으로 저장하고, 선택한 배치가 모두 성공한 뒤 명시적 안전 checkpoint만 갱신한다. 큰 merge 그룹은 여러 실행으로 나눌 수 있고, 저장된 SHA는 재사용한다. 전체 그래프·진행 SHA 개수·시간·메모리 상한은 여전히 존재한다.

관련 코드: [Git 수집](../source/src/main/java/com/aicreviewer/git/GitRepositoryClient.java), [AI 입력/출력 검사](../source/src/main/java/com/aicreviewer/ai/AiReviewClient.java), [저장과 배정](../source/src/main/java/com/aicreviewer/review/ReviewRepository.java), [이슈 상태](../source/src/main/java/com/aicreviewer/issue/IssueService.java).

## 2. 유지할 원칙

1. **변경 목록의 완전성**과 **그 내용을 검토한 범위**를 따로 증명한다. 파일 목록조차 불확실한 커밋은 수동 이슈 하나로 성공 처리하지 않는다.
2. 고정된 커밋 SHA와 첫 부모 SHA를 사용한다. 실행 중 이동할 수 있는 branch HEAD의 blob으로 누락 내용을 채우지 않는다.
3. 파일 확장자, 모델의 추정, 빈 patch만으로 binary·무변경·안전을 선언하지 않는다. “크기가 커서 형식을 확인하지 못함”과 “binary임을 확인함”도 구별한다.
4. 모든 변경 경로에 처리 결과가 있어야 한다. 잘림·인증 오류·네트워크 오류를 일반적인 `SKIPPED`로 바꾸지 않는다. 알 수 없는 분류는 실패한다.
5. AI 응답 실패·시간 초과·출력 잘림을 자동으로 수동 검토 성공으로 낮추지 않는다. 입력 범위의 정책과 모델 호출 실패는 별개다.
6. 본문 미검토 파일이 있으면 목록·요약·이슈·집계에서 계속 드러나야 한다. 수동 상태 변경으로 과거의 AI 검토 범위를 다시 쓰지 않는다.

## 3. 파일별 판단 제안

아래 표는 새로운 처리를 허용하기 위한 **증거 요건 제안**이다. 현재 API가 각 증거를 항상 제공한다는 주장은 아니다. 대상 GitHub/GitLab 버전의 공식 API 문서와 실제 응답 fixture로 확인한 뒤 구현한다.

| 상황 | 필요한 증거 | 제안 처리 |
|---|---|---|
| 지원되는 완전한 text 변경 | 전체 변경 manifest, 부모/현재 blob 식별자, 완전한 본문 또는 검증한 patch, 경로·모드·통계의 일치 | 모든 text 범위를 AI 검토. 예산에 맞으면 기존 단일 호출 유지 |
| patch 없는 동일 blob rename/mode 변경 | 양쪽 고정 트리의 동일 blob ID, 정확한 이전/새 경로와 모드, 추가·삭제/유지 경로까지 맞는 manifest | GitHub에도 검증된 메타데이터 경로 확장. 파일 유형·symlink·실행권한을 명시. AI 본문 검토 주장은 금지 |
| 확인된 binary의 추가·수정·삭제 | 완전한 manifest와 blob 식별자, 제한 안에서 확인한 내용 형식 또는 검증 가능한 공급자 증거 | 승인된 수동 정책이 있다면 해당 파일의 수동 이슈와 범위를 원자적으로 저장. 없으면 현재처럼 실패 |
| 크기 상한을 넘는 알려진 blob | 완전한 manifest, 고정 blob ID/크기와 초과한 예산. 내용 전체를 읽지 않았으면 binary라고 단정하지 않음 | `크기 제한으로 본문 미검토` 후보. 수동 정책이 없으면 실패 |
| API patch 누락/`collapsed`/`too_large` | 이 신호만으로 완전성은 입증되지 않음 | 독립적인 고정 tree/blob 경로로 목록·본문을 재구성하고 일치를 확인할 수 있을 때만 재분류. 그렇지 않으면 실패 |
| 파일 목록 잘림, pagination 상한, 통계 불일치, 누락된 부모/경로, 재작성된 cursor | 필요한 증거 부족 | 실패 유지. 수동 이슈 생성만으로 cursor 진행 금지 |
| 401/403/404, rate limit, timeout, 잘못된 JSON, 응답 크기 초과 | 소스가 존재하지 않는 것인지 권한/전송 문제인지 불확실 | 실패·재시도/운영 조치. 확인된 삭제로 해석하지 않음 |

완전한 manifest는 text 통계 합계만으로 대체하지 않는다. binary나 mode-only 변경은 추가·삭제 행이 0이어도 실제 변경일 수 있다. GitHub의 재귀 tree가 잘렸거나 공급자 파일 목록의 한계를 만난 경우에는 검증된 하위 tree 순회 같은 별도 수집 경로가 필요하다. 그 경로 자체의 응답·페이지·메모리 예산을 넘으면 실패한다.

blob 내용을 받는 경우, 공급자가 준 식별자·길이와 실제 데이터를 검증하는 방법을 명시한다. Git 객체 ID는 단순 파일 SHA와 같다고 가정하지 않는다. 전체 blob을 읽지 않은 경우에는 “blob ID/크기 메타데이터 확인”이라고만 기록하고 전체 바이트 무결성을 검증했다고 표시하지 않는다. LFS pointer는 외부 객체 본문이 아니다. LFS 다운로드·submodule clone·archive 해제·symlink 추적은 이 설계의 자동 동작에 포함하지 않는다.

## 4. 수동 검토 정책과 화면 의미

권장 출발점은 **현재의 엄격한 실패 정책을 기본값으로 유지**하는 것이다. 구조화된 파일별 범위를 먼저 도입한 뒤, 관리자가 프로젝트별로 승인한 범위에 한해서 확인된 미검토 파일을 이슈로 전달하는 기능을 제안한다. 아직 설정 이름·기본 허용 분류는 정하지 않았다.

수동 정책을 허용한다면 커밋의 처리 완료와 사람의 검토 완료를 분리한다.

- 실행 성공: 변경 목록을 확인하고 AI 결과 또는 승인된 수동 업무를 빠짐없이 영구 저장했다는 의미다. “전부 AI 검토 완료”로 표시하지 않는다.
- 화면: 예를 들어 `AI 검토 3파일 / 수동 확인 대기 2파일`. AI 권고와 수동 업무의 수를 분리하고, “이슈 없음”으로 미검토가 가려지지 않게 한다.
- 수동 이슈 `OPEN`: 본문 또는 메타데이터 검토가 남음. `RESOLVED`: 담당자가 수동 검토 완료를 명시하고 검토 내용·근거를 기록함. `DISMISSED`: 사유가 있는 검토 예외 처리이며 “문제 없음”과 구별한다.
- 상태 변경자·시각·사유를 감사 기록으로 보존한다. 기존 담당자/관리자 접근 범위가 기본이다. 예외 처리를 관리자에게만 제한할지는 남은 정책 결정이다.
- 원본 커밋과 파일 증거를 연결한다. 개인 Git 서버 권한은 별도이며 링크 제공으로 소스 접근 권한을 부여하지 않는다. 이메일·토큰·소스 원문을 감사 로그에 넣지 않는다.
- 현재 `검토가 완료된 이력의 기준 커밋` 안내는 수동 정책 도입 시 `처리된 이력의 기준 커밋` 등의 표현으로 바꾸고, 미완료 수동 업무가 별도로 남음을 표시해야 한다.

현재 `METADATA_ONLY` 결과에 이슈를 자동으로 소급 생성하지 않는다. 과거 항목을 다시 검토할지는 명시적 재처리 작업과 이력 정책으로 정해야 한다. 기존 SHA 중복 방지를 해제하거나 기존 커밋 결과를 삭제하는 방식은 권장하지 않는다.

## 5. 구조화된 범위와 데이터 변경 후보

다음은 마이그레이션 검토를 위한 필드 후보이며 확정 DDL이 아니다. 다음 Flyway 번호는 구현 시점에 정한다.

| 대상 | 제안 변경 | 이유 |
|---|---|---|
| 파일별 범위 테이블 | 커밋 FK, 안정적인 변경 key, 이전/새 경로, 이전/새 blob ID·모드, 변경 종류, 처리 분류, 증거 종류·크기·제한 사유 | 설명 문자열을 역파싱하지 않고 누락과 수동 범위를 검증 |
| `reviewed_commit` | 기존 범위에 `MIXED_MANUAL`/`MANUAL_ONLY` 같은 명시적 후보 추가, 범위/계획 버전 기록 | 일부 text만 검토한 커밋을 `FULL`로 저장하지 않음 |
| `review_issue` | `issue_kind=AI_FINDING/MANUAL_REVIEW`, 파일 범위 FK, 수동 완료/예외 사유 | 수동 업무를 모델이 찾은 결함처럼 표현하지 않음 |
| 이슈 심각도 | 수동 업무는 결함 심각도를 모르는 상태로 표현. `MANUAL_REVIEW`에서만 severity null 허용 등의 CHECK 검토 | 근거 없이 모든 미검토 파일을 MEDIUM 취약점으로 만들지 않음 |
| 이슈 위치 | 기존 실제 `file_path`와 nullable 행 번호 유지. 삭제/rename은 구조화된 이전·새 경로 참조 | `(커밋 메타데이터)` 같은 가짜 파일 경로를 만들지 않음 |
| 청크별 처리 기록 — 후속 단계 | 계획 digest, 파일/행 범위, prompt/model/config 버전, 완료 상태, 결과 fingerprint | 중단 후 동일 범위의 재호출·중복 권고를 제어. 본문 저장 여부는 별도 결정 |

파일별 변경 key는 커밋과 이전/새 경로·blob·모드 등 고정된 항목의 정규 직렬화에서 생성한다. AI 문장이나 실행 시각을 key로 사용하지 않는다. 파일 범위와 커밋/프로젝트 FK의 일관성을 DB 제약으로 유지한다. 수동 이슈는 기본적으로 변경 파일당 1건을 제안하며, `(reviewed_commit_id, file_coverage_id, issue_kind)`의 부분 UNIQUE 같은 제약으로 중복을 막는다. 수동 사유가 여러 개면 같은 파일의 범위에 모두 보존한다.

파일 수·수동 이슈 수·저장할 설명의 총량에도 상한이 필요하다. 상한을 넘는 나머지 파일을 버리거나 임의로 처음 N개만 이슈화하지 않는다. 큰 커밋을 그룹 업무로 표시하려면 완전한 첨부 manifest와 모든 변경 경로의 연결을 먼저 설계해야 한다. 첫 단계에서는 상한 초과 시 실패하는 편이 명확하다.

기존 결과에는 범위 증거가 부족하므로 migration에서 과거 `FULL`을 새 증거로 검증된 것처럼 승격하지 않는다. 기존 이슈를 `AI_FINDING`으로 유지하고 과거 범위에는 기존 형식/버전임을 표시한다. 새 enum을 도입할 때 DB CHECK·coordinator allowlist·JSP·집계를 함께 바꾸고, 구버전 앱과 혼용하지 않는다. schema 하향 변경 전 새 분류 데이터의 보존 전략도 필요하다.

## 6. 트랜잭션·배정·진행 위치

커밋 하나의 최종 저장은 다음 항목이 모두 준비된 뒤 한 트랜잭션으로 수행하는 구성을 권장한다.

1. 전체 변경 manifest와 파일별 처리 계획을 검증한다. 필요 AI 호출이 모두 정상 종료되고 결과의 경로·행 범위도 확인되어야 한다.
2. 프로젝트 승인 상태와 기존 cursor를 row lock 아래 재확인한다. 커밋의 기존 UNIQUE 키가 있으면 결과/업무를 중복 생성하지 않는다.
3. 커밋 범위, 파일별 증거, AI 권고, 수동 업무, 실행 건수와 감사 기록을 함께 저장한다. 하나라도 실패하면 커밋 단위로 전부 rollback한다.
4. 배치 전체의 선택 항목이 저장된 뒤 기존 `GitReviewBatch.checkpointSha` 계약으로 안전한 진행 위치만 갱신한다. 부분 merge는 결과가 저장되어도 null checkpoint를 유지할 수 있다.

배정은 기존 우선순위를 재사용한다: GitHub.com 계정의 활성 사용자 → 정확한 origin/전체 이메일의 활성 사용자 매핑 → 프로젝트 소유자. 수동 업무만 다른 문자열 추론으로 배정하지 않는다. 배정 결과와 근거를 해당 커밋 저장 시 확정하고 재시도 때 이미 생성된 업무의 담당자를 조용히 바꾸지 않는다. 소유자가 비활성이어도 업무를 누락하지 말고 기존 관리자 조회/후속 재배정 정책에서 다룬다.

수동 이슈 생성 후 cursor를 이동할지는 **승인된 수동 정책의 핵심 결정**이다. 위 제안에서는 등록된 수동 업무를 처리 완료로 인정하되 사람의 확인은 별도로 추적한다. 엄격한 정책에서는 파일을 수동 업무로 넘긴 것만으로 `reviewed_commit` 완료나 cursor 진행을 허용하지 않는다. 두 방식을 같은 성공 표시로 섞지 않는다. 수동 업무 종료 자체가 과거 cursor를 다시 쓰거나 새로운 AI 실행을 뜻하지도 않는다.

권한 변경·pause·중단·DB 오류·작업자 재시작 때도 현재 advisory lock과 승인 재검사를 유지한다. 새로운 per-file/청크 저장 단계가 생기면 임시 결과가 `reviewedShas`에 완료된 커밋처럼 포함되지 않아야 한다.

## 7. 큰 text 변경과 context 처리 제안

전체 text를 얻을 수 있다는 사실과 한 번의 모델 입력에 들어간다는 사실은 다르다. 첫 단계는 **검증된 파일 경계별 분할**, 다음 단계는 **파일 내부 hunk 단위 분할** 순서가 적절하다.

- 공급자 patch가 잘렸다면 고정된 양쪽 blob에서 제한된 diff를 재구성하는 경로를 별도로 검증한다. 받은 앞부분만 잘라 사용하지 않는다. 파일 길이·인코딩·줄바꿈·전체 변화량과 경로 대응을 확인한다.
- 모든 변경 행이 적어도 한 입력에 포함되는 계획을 만들고 coverage map으로 누락·중복 경계를 검증한다. context 행의 겹침은 허용하지만 동일 결함의 이슈 중복은 별도로 제어한다.
- 각 입력은 실제 JSON 직렬화 후 prompt·스키마·출력·여유분 예산을 적용한다. 현재 보수적 UTF-8 byte 기준을 단순 평균 token 비율로 약화하지 않는다. 정확한 tokenizer 적용은 provider/model별 검증이 먼저다.
- UTF-8 문자·hunk 헤더·파일 경로를 중간에서 자르지 않는다. 원본 old/new 행 번호를 유지한다. 한 행 자체가 예산을 넘으면 그 행을 조각내어 정상 본문이라고 속이지 않고 명시적으로 실패하거나, 승인된 미검토 정책으로 분류한다.
- 새 파일은 현재 blob, 삭제 파일은 부모 blob, rename은 양쪽 경로를 기준으로 한다. 삭제된 행을 새 파일의 양수 행으로 표시하지 않는다. 현재 스키마에서는 삭제 지적의 행을 null로 제한하고, 후속 `OLD/NEW/NONE` 위치 모델을 검토할 수 있다.
- AI 응답은 해당 청크에 실제로 제공한 경로·행 범위로 검증한다. 전체 커밋의 다른 파일에 대한 추측을 통과시키지 않는다. 메타데이터-only 파일은 body hunk가 있는 것처럼 만들지 않는다.
- 마지막 청크의 실패나 출력 잘림도 커밋 완료를 막는다. 비용·시간을 줄이는 임시 청크별 처리 기록은 후속 기능으로 분리하고, 계획/모델/프롬프트 버전이 달라지면 재사용 조건을 다시 판단한다.
- 동일 finding의 중복은 안정적인 파일·행·결함 근거에 따라 통합하되 서로 다른 결함을 제목 유사도만으로 합치지 않는다. 전체 청크의 이슈 수가 기존 출력 상한을 넘으면 조용히 자르지 않는다.
- 파일 간·청크 간 상호작용은 분할만으로 충분히 검토되지 않을 수 있다. 집계 요약은 이 한계를 명시해야 하며 “모든 맥락을 AI가 검토했다”는 주장을 하지 않는다. 추가 통합 검토도 자체 context 예산과 품질 평가가 필요하다.

청크 수·파일별 raw 크기·커밋 전체 다운로드 크기·총 API 호출·실행 시간·worker 메모리 예산을 함께 설정해야 한다. 기존 100커밋 배치가 무제한 청크 호출로 변해서는 안 된다. 로컬/원격 모델 모두 동일한 범위 검증을 적용하고, 유료/외부 호출 비용과 소스 전송 범위는 배포 정책으로 정한다.

## 8. 검증 계획

| 영역 | 필수 사례와 확인할 결과 |
|---|---|
| 공급자 fixture | GitHub 동일 blob rename/mode, 유지 원본을 가진 copy, symlink 전환, GitLab binary·too_large, 삭제·새 빈 파일, 혼합 변경, stats 0이지만 변경 존재 |
| 완전성 반례 | 잘린 tree/list, pagination 한계, 누락 경로, header-only patch, 다른 SHA 응답, 경로/통계 불일치 → 실패·cursor 유지 |
| 증거와 분류 | 확장자만 binary인 text, LFS pointer, 전체를 읽지 못한 큰 blob → 확인한 증거 수준만 표시 |
| 청크 경계 | 한글·다중 byte, CRLF, 마지막 개행 없음, 거대 한 행, hunk 경계, 삭제 old-line, rename 경로, context 겹침, JSON overhead 상한 ±1 |
| 실패 원자성 | 마지막 AI 호출 실패, 수동 이슈/FK/audit 저장 실패, 최종 checkpoint 실패 → 커밋 단위 rollback 또는 이전에 완료 저장된 커밋만 재사용 |
| 재시도/동시성 | 동일 SHA·같은 파일 수동 업무 중복 없음, pause/재시작/두 인스턴스, partial merge, 새 head와 orphan 저장 SHA, 모델/계획 버전 변경 |
| 배정/권한 | 기존 작성자 배정 우선순위·비활성 fallback, 담당자/관리자만 조회/변경, 다른 프로젝트 이메일/URL 정보 비노출, CSRF·XSS |
| 실제 PostgreSQL | migration 전후 기존 FULL/이슈 보존, 새 CHECK/FK/UNIQUE, commit+파일범위+업무 rollback, 백업/복원 후 동일한 업무 상태와 진행 위치 |
| 화면/품질 | AI 권고와 수동 업무 구별, 미검토 수/사유/원본 링크, 완료/예외 감사, 모바일/키보드, binary 미검토를 결함 없음으로 오인하지 않음 |

기본 검증은 합성 HTTP fixture와 격리 DB를 사용한다. 실제 GitHub/GitLab 서버의 지원 버전별 smoke는 별도 opt-in으로 수행한다. 프로토콜·범위 테스트 통과는 모델의 결함 탐지 품질 합격과 별개이며 [AI-EVALUATION.md](AI-EVALUATION.md)의 평가를 확장해야 한다.

## 9. 우선순위와 남은 결정

| 순서 | 작은 구현 단위 제안 | 완료 조건 |
|---|---|---|
| 1 | 현재 실패 사유를 공급자/파일/증거 기준으로 정리하고 구조화된 manifest 계약 확정 | 실패를 성공으로 바꾸지 않은 채 대표 fixture와 불완전성 반례 통과 |
| 2 | GitHub 동일 blob rename/mode 증명 경로 | GitLab과 같은 명시적 범위·symlink 안내, copy/누락/binary 오인 차단. 아직 일반 binary 허용은 하지 않음 |
| 3 | 파일 범위 migration과 수동 업무 모델/화면 | 기존 데이터 보존·배정·권한·원자성·멱등성 검증. 미승인 프로젝트에서는 기능 비활성 |
| 4 | 승인한 범위의 verified binary/oversized 수동 정책 | 모든 경로의 증거·업무가 저장될 때만 합의한 cursor 정책 적용; 불명확한 API 누락은 계속 실패 |
| 5 | 제한된 text 복구와 파일별/청크별 AI 검토 | 전체 변경 행의 coverage, 총 예산, 중단 재시도, 삭제/rename 위치 및 모델 품질 검증 |

먼저 결정할 사항은 수동 업무 등록만으로 이력 처리를 진행할지, 허용 분류와 프로젝트 승인 방식, 수동 예외 처리 권한·필수 근거, 파일당 업무 수/상한, 임시 본문·AI 결과의 보존/삭제 정책이다. 큰 blob의 실제 수집 경로·해시 검증과 공급자 API 한계는 조사 결과에 따라 설계가 달라질 수 있다.

이 확장만으로 전체 릴리스 과제가 끝나지는 않는다. 전체 역사/메모리 상한, 실제 설치형 GitLab·LiteLLM 호환, 모델 지연·품질, 장시간 장애 복구와 운영 보안 검증은 별도 남는다. 어느 단계도 미확인 변경을 검토 완료로 숨기는 방식으로 통과시키지 않는다.
